## 0.1.8 接受控制、输入保持和设备导航回退修复

- 接受控制日志显示首次启动在约 549 毫秒收到 `info` 后失败，随后两次只收到未启动状态并各等待约 70 秒；尚未执行 Sunshine 防火墙步骤。首次原生提示未保留，不能断言其具体原因。修复了已确认的清理缺口：发送启动后记录未完成状态，失败后真正发送停止命令并等待确认；未确认时保留状态，下次开启先重试停止。仅收到未启动状态时不再持续等完整网卡初始化预算，同时允许随后到来的正常初始化继续执行。正常慢初始化仍保留原有预算。
- 本地 WebSocket 缺失初始状态时清理未完成的连接，避免后续把它当成已初始化接口；客户端组网连接存在时明确要求先断开，不自动中断该连接。
- 密码监听从返回新数组改为逐值监听，后台快照不再清空输入。输入编辑、迟到请求、提交期间修改及同窗口切页保留草稿；草稿按已确认账号隔离，旧账号读取失败或迟到开启结果不覆盖新账号。
- 设备列表按已有 ID 保持位置，同时使用最新状态对象；新设备追加、删除移除，收藏分组与账号切换保持正常。协助页将接受控制、三项分享信息与复制入口集中到一个紧凑区域，去掉重复长说明。
- 本机旧 0.1.6 网络宿主在确认精确程序路径、相同文件哈希、父进程已不存在、无主程序/Sunshine/客户端连接后，通过原控制事件正常退出；225 毫秒确认退出，端口释放，没有强杀、删除驱动或用户数据。此结果不等同于新版接受控制或双机串流已经实机通过。

Rust 回归 50 项通过、4 项按原标记忽略；前端单元 34 项通过，输入保持与账号隔离包含 16 项专项检查。两种窗口尺寸的协助页已进行浏览器布局检查。完整构建、页面回归、数据迁移及实机待验范围见 [0.1.8 验证记录](validation/0.1.8.json)。

## 0.1.6 网卡故障定位与验证

- 实机根因是旧离线 Wintun 设备的持久 LUID 索引 32768 与运行时索引 32770 冲突，新接口被分配到已占用的 32770 后，NDIS 拒绝创建 GUID 关联。管理员、x64 管理员、SYSTEM 和显式加载驱动均复现同一错误。保存原始记录后，用 Windows 标准设备管理接口仅移除该离线设备，随机 GUID 一次、旧 SDK GUID 两次创建和收发会话均成功，创建耗时分别为 265、172、188 毫秒。
- 启动等待按 VPN 配置、Wintun 初始化、服务就绪分阶段处理，总预算 90 秒，保留完整 20 秒服务就绪等待。兼容内核原有 `loading/hied` 拼写，网卡错误直接返回。
- 固定版本网络宿主经过 SDK 哈希和内存布局校验后接管原生 Wintun 日志，保存数值诊断并保留调用线程错误码。Rust 校验当前 PID、操作开始时间及固定初始化阶段，清理日志和旧错误文件不会覆盖本次真实失败。主动连接、后台启动和诊断页统一展示原始 Windows、设备问题和 NTSTATUS 代码。
- 无法确认停止时保留窗口和宿主所有权，提供错误提示及再次尝试。
- Rust 34 项、前端单元 14 项、网页界面 10 项全部通过，另有 4 项按原标记忽略的原生场景。类型检查、生产构建、原生日志模拟及真实隔离宿主启动通过。138 个本机二进制和 1597 个发布资源校验通过。

0.1.6 已由实际用户界面开启本机接受控制：真实皎月连 SDK 返回运行状态，Sunshine 本机 HTTPS 返回 200，Wintun 设备状态为 OK、网卡为 Up，持久与运行 LUID 均对应索引 32768。服务保持开启。用户确认已删除旧版目录，使用新版完成账号设置与登录；本轮没有从旧版迁移或恢复数据。

详见 [故障排查](虚拟网卡创建故障排查.md) 与 [0.1.6 验证记录](validation/0.1.6.json)。另一台电脑的组网、配对、串流及 Windows 重启后的持续恢复仍待验收。

- 同一设备重连按已确认 Sunshine UUID 合并，UUID 冲突保留独立设备。载入旧文件时整理重复记录，保留设备 ID、昵称、收藏、壁纸、画质、有效凭据和历史引用。

- 管理员自启动使用当前用户的 HighestAvailable / InteractiveToken 计划任务，注册后回读验证，迁移失败恢复旧任务。
